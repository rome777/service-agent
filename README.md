### 자동차 수리 예약 챗봇 설계

#### 서비스 소개

"바른정비" 정비소(강남점, 마포점)의 예약 안내 챗봇이다. 고객은 영업시간이나 예약 규정을 묻고, 빈 시간을 확인하고, 예약 요청을 넣을 수 있다. 예약 확정, 수리비 견적, 사고·보험 수리는 챗봇이 하지 않고 정비소 담당자가 맡는다.

구현은 하지 않았다. 챗봇이 어디까지 하고 어디서 멈출지를 문서로 정했다. 자세한 설계는 [design-packet.md](design-packet.md)에 있다.

#### 설계 결정 요약

**도구를 세 개만 둔 이유**

예약 상담에 꼭 필요한 일은 정책 묻기, 빈 시간 확인, 예약 넣기 세 가지였다. 예약 조회, 변경, 취소는 남의 예약을 보거나 바꿀 위험이 있어서 도구로 만들지 않고 담당자에게 넘겼다. 세 도구는 쓰는 때가 서로 겹치지 않게 나눴고, "언제 돼요?"는 빈 시간 확인, "예약해 주세요"는 예약 요청으로만 가게 했다.

**권한을 나눈 기준**

정보를 읽기만 하는 도구(정책 찾기, 빈 시간 확인)는 승인 없이 쓰게 했다. 정비소 일정에 무언가를 남기는 예약 요청만 쓰기 도구로 두고, 고객 확인을 받은 뒤에만 하네스가 실행하게 했다. 그래도 예약은 "요청" 상태로만 들어가고, 확정은 담당자가 한다.

**실패 뒤 행동을 그렇게 정한 근거**

읽기 도구는 한 번 더 해 봐도 손해가 없어서 재시도 한 번을 허용했다. 예약 요청은 다시 해 보면 예약이 두 번 들어갈 수 있어서 재시도하지 않고 바로 담당자에게 넘긴다. 같은 오류가 두 번 나면 모델이 같은 호출을 되풀이하지 않도록 멈춘다.

#### 실행하지 않은 것과 이유

| 하지 않은 것 | 이유 |
|---|---|
| 세 도구의 실제 구현 | 과제 범위가 설계 문서까지다. 진짜 정비소 일정 시스템과 안내 문서도 없다 |
| 테스트 문항 8개 실행 | 도구가 없어서 돌릴 수 없다. 기대 행동만 적어 두었다 |
| 정책 문서 검색 정확도 확인 | 실습에서 쓴 Qdrant 서버의 기본 임베딩 모델은 영어용이다. 한국어 문서로 얼마나 잘 찾는지 재 봐야 한다 |

다음에 잴 것
- 테스트 문항 8개를 실제 모델에 넣었을 때 기대 도구, 기대 반환 필드, 기대 중단·이관과 몇 개나 맞는지
- 확인 전에 `request_reservation` 을 부르려는 시도가 몇 번 나오는지, 하네스가 그걸 다 막는지
- 한국어 정책 질문에서 맞는 조항이 1위로 나오는 비율
